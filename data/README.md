# Data

Every dataset in this repository states where it came from. This is not
bookkeeping: a drag table with unknown provenance produces a solver with unknown
accuracy, and synthetic data mistaken for measurement teaches the reader to
trust numbers that were invented.

## The rule

Every dataset gets an entry below stating:

1. **What it is** — the quantity, the units, the format.
2. **Where it came from** — a citation, or "synthetic, generated by `<script>`".
3. **When** it was created or retrieved.
4. **What was assumed** — for synthetic data, exactly what model produced it.

Synthetic data is labelled synthetic in **three places**: the file header, the
lesson that uses it, and here. Its generator script is committed.

## Format conventions

- CSV, UTF-8, with a header row.
- Column names carry units, matching the code convention: `range_m`,
  `velocity_mps`, `drop_in`.
- A `#`-prefixed comment block at the top of each file states its provenance in
  one or two lines, so a file separated from this README is still traceable.

## Datasets

### `drag_tables/`

**Status:** not yet created — Module 13 builds these.

Standard drag functions G1, G2, G5, G6, G7, G8 as two-column Mach / $C_D$
tables. Module 13 must record the specific published source used, and note that
the G-family curves originate from Ballistic Research Laboratory work (the G1
function descending from Mayevski and Ingalls). The entry must also state which
atmospheric standard the tables assume — ICAO or Army Standard Metro — because
older G1 ballistic coefficients were computed against the latter, and the ~0.5%
density difference matters.

### `dope/`

**Status:** not yet created — Module 28 builds these.

Three **synthetic** DOPE datasets for the course's running load: clean,
realistically noisy, and transonic-contaminated. Generated by a committed script
from a known ground-truth muzzle velocity and ballistic coefficient, so that
truing can be checked against the answer it should recover.

These are synthetic because real DOPE from an identified shooter and rifle is
not ours to publish, and because a known ground truth is what makes the truing
exercises verifiable. Module 28 must say so plainly.

### `modules/00-orientation/data/effect_magnitudes.csv`

**Status:** created by Module 00.

**What it is.** Drop, wind deflection, spin drift, aerodynamic jump, and
Coriolis (horizontal and vertical) for the course's running load, at 100-yard
increments from 100 to 1200 yards. Ranges in yards, every effect in inches;
column names carry their units.

**Where it came from.** **Synthetic — model output, not measurement.**
Generated by `modules/00-orientation/data/generate_effect_magnitudes.py`, which
is committed alongside it. That script is a standalone reference implementation:
it imports nothing from `src/ballistics/`, and it is deliberately *not* the
library the reader is about to build. Module 00 needs numbers before the reader
has a solver, and inventing a citation would be worse than generating the data
and saying so.

**When.** Created 2026-08-29.

**What was assumed.** A G7 point-mass model integrated with RK4, at ICAO sea
level; the running load (6.5 Creedmoor, 140 gr Berger Hybrid Target, G7 BC
0.315 lb/in², 2700 fps, 1:8 right-hand twist, 1.75 in sight height, 100-yard
zero); a 10 mph full-value crosswind from 3 o'clock; latitude 45° N; and a
firing azimuth of 90° (due east). The exact values are restated in the file's
own header block.

Three of its columns are **empirical fits, not physics**, and the generator says
so at each one: spin drift and aerodynamic jump follow Litz's approximations,
and the gyroscopic stability factor they need comes from Miller's rule. Module
21, Module 22, and Module 20 respectively treat each properly.

Module 17 regenerates this file from the reader's own solver and diffs it. That
loop means something precisely because the two implementations are independent,
and because Module 00 was honest about where its numbers came from.
